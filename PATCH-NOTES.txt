Redis ingress state-machine repair:
- Fixed a real duplicate-live-prompt race in uncertain HTTP recovery.
- The original defer timer and startup recovery could both schedule the same uncertain record.
- Previously each contender could XADD the same logical prompt before either HDEL removed the uncertain source.
- Requeue is now serialized with a per-record Redis lock and re-reads the durable record after acquiring ownership.
- Replacement XADD + uncertain HDEL execute in one Redis transaction.
- Suppressed prompt IDs remain a hard retry gate.
- /queue and /queue-full no longer call ACKed-but-preserved historical ingress rows "queued".
- Queue visibility fails open if consumer-group metadata cannot be read.

Audit findings:
- Worker-side chain replacement, dependency parking, child parking and cooperative yield already use Redis MULTI/EXEC where atomic replacement is required.
- Worker-side park_chain/revise_retry/escalate/reclaim paths still contain sequential XADD/ACK/XDEL operations. These are recoverability/hardening candidates, but they do not explain the duplicate GUI prompt IDs shown in the reproduced incident.
- Suppression deliberately preserves some ACKed stream rows for inspection until explicit cleanup; those rows are storage, not executable live work.
- The reproduced duplicate prompt IDs originate in the independent GUI ingress uncertain-retry layer.

Regression tests:

- ACKed historical rows are excluded from the LIVE QUEUE snapshot.
